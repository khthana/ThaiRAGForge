1โปรเจกต์นี้คืออะไร และทำไมมันยาก

โปรเจกต์นี้สร้างเฟรมเวิร์กทดลองเพื่อตอบคำถามว่า ในระบบ RAG บนเอกสารมติสภาวิชาการ ภาษาไทย การเลือกองค์ประกอบแต่ละส่วนแบบไหน ทำให้ค้นหาเอกสารที่เกี่ยวข้องได้แม่นที่สุด — และคำถามเชิงวิจัยที่ลึกกว่านั้นคือ embedding model ที่เทรนมาเพื่อภาษาไทยโดยเฉพาะ สู้โมเดล multilingual หรือโมเดลที่สร้างจาก LLM ได้หรือไม่ เมื่อคิดทั้งคุณภาพและต้นทุน

ทฤษฎี — RAG และขอบเขตของโปรเจกต์นี้ RAG (Retrieval-Augmented Generation) คือการให้ LLM ตอบคำถามโดยอ้างอิงเอกสารจริง แทนที่จะตอบจากความจำในตัวโมเดล มี 3 ขั้น: (1) Index — ตัดเอกสารเป็นชิ้นเล็ก แล้วแปลงเป็นเวกเตอร์เก็บไว้ล่วงหน้า (2) Retrieve — แปลงคำถามเป็นเวกเตอร์ แล้วดึงชิ้นเอกสารที่ใกล้เคียงที่สุด (3) Generate — ป้อนชิ้นที่ได้ให้ LLM เขียนคำตอบ

โปรเจกต์นี้ทำเฉพาะขั้น (1) และ (2) ไม่รวมขั้นที่ 3 เพราะถ้า retrieval ดึงเอกสาร ผิดตั้งแต่ต้น ไม่ว่า LLM จะเก่งแค่ไหนก็ตอบถูกไม่ได้ — จึงต้องหาให้ได้ก่อนว่า "องค์ประกอบไหนทำให้ retrieval แม่นที่สุด"

คลังข้อมูลที่ใช้

เอกสารมติสภาวิชาการ สจล. จำนวน 2,853 ไฟล์ จัดเรียงเป็น ปี(พ.ศ.)/ครั้งที่ N/<เรื่อง>.md ทุกไฟล์ผ่านการ OCR มาจาก PDF สแกน ซึ่งเป็นที่มาของปัญหาใหญ่ที่สุดของโปรเจกต์นี้ (ดูเฟส 3)

ทำไมงานนี้ยากกว่าที่คิด — 4 เหตุผล

  1. ข้อความมาจาก OCR ที่ไม่สมบูรณ์ — ไม่ใช่แค่พิมพ์ผิดประปราย แต่มีทั้งการวนลูปซ้ำ ข้อความมั่วที่อ่านดูเหมือนภาษาไทยแต่ไม่มีความหมาย และหน้าที่หายไปทั้งหน้า ซึ่งสิ่งเหล่านี้ ทำลายการค้นแบบจับคู่คำ (lexical) มากกว่าการค้นแบบเวกเตอร์ จึงบิดผลการเปรียบเทียบอย่างไม่สมมาตร
  2. ภาษาไทยไม่มีช่องว่างระหว่างคำ — การตัดคำต้องใช้ dictionary หรือโมเดล และ tokenizer ที่ต่างกันให้ผลต่างกัน ส่งผลถึงทั้ง BM25 และการตัด chunk
  3. 1 คำถามมีคำตอบถูกได้หลายข้อ — เฉลี่ย 8.8 มติต่อคำถาม สูงสุด 43 ซึ่งทำให้ metric มาตรฐานอย่าง recall@10 มี เพดานเชิงโครงสร้าง ที่ต่ำกว่า 1.0 มาก (ดู §7.5)
  4. ทุกครั้งที่ข้อมูลเปลี่ยน ตัวเลขทั้งหมดต้องสร้างใหม่ — index หนึ่งชุดคือ 4 chunker × 9 embedder = 36 combo ใช้เวลา GPU หลายชั่วโมงถึงหลายวัน และมันเกิดขึ้น 3 รอบ (ดูเฟส 6)

2ภาพรวม — งาน 3 ก้อนและเส้นเวลา

งานทั้งหมดแบ่งได้เป็น 3 ก้อนที่พันกันอยู่ตลอด ไม่ได้ทำจบเป็นลำดับ:

ก้อนคืออะไรเวลาจริง
A. เฟรมเวิร์กโค้ด 4 แกนที่สลับได้ + Streamlit UI + CLI + ชั้นวัดผล~2 วัน (จบเร็วผิดคาด)
B. คุณภาพข้อมูลกระทบยอดคอร์ปัส, แยกไฟล์รวมหลักสูตร, ล้าง OCR เสีย, tag entity~15 วัน (ก้อนใหญ่ที่สุด)
C. การทดลอง + สถิติ36 combo, BM25, hybrid, ablation, reranker, significance test~10 วัน
ข้อสังเกตสำคัญที่สุดของโปรเจกต์ ก้อน B ไม่ใช่ "งานเตรียมข้อมูล" ที่ทำครั้งเดียวจบ — มันกลับมาทำลายตัวเลขของก้อน C ถึง 3 รอบ และทุกรอบต้อง rebuild index ทั้งหมด แล้วรัน eval ใหม่หมด ถ้าจะสรุปโปรเจกต์นี้เป็นประโยคเดียว: "เวลาส่วนใหญ่ไม่ได้หมดไปกับการทดลอง แต่หมดไปกับการทำให้แน่ใจว่าสิ่งที่ทดลองอยู่คือข้อมูลจริง"

4เฟส 2 — จัดระเบียบคอร์ปัส (3–7 ก.ค.)

4.1 กระทบยอดคอร์ปัส

เทียบรายการมติที่ควรมีตามเอกสารต้นทาง กับไฟล์ที่มีอยู่จริงในดิสก์ สร้าง master_list.csv เป็นแหล่งความจริงเดียว

ผลลัพธ์ ปิดสมบูรณ์ 2,853 / 2,853 รายการ ครบทุกไฟล์ ไม่มีอะไรค้างและไม่มีใครติดค้างงานใคร

4.2 แยกไฟล์รวมหลักสูตร (ADR-0004)

พบว่าบางไฟล์บรรจุมติของหลายหลักสูตรรวมกันอยู่ในไฟล์เดียว ซึ่งขัดกับ ADR-0002 ที่ถือว่า 1 ไฟล์ = 1 Resolution โดยตรง — ถ้าไม่แยก การวัด recall จะผิดตั้งแต่ต้น เพราะระบบจะนับว่า "ตอบถูก" ทั้งที่ดึงมติคนละหลักสูตรมา

ผลลัพธ์ แยก 178 ไฟล์ ออกเป็น 528 ชิ้น — และระหว่างทางเจอ defect แรกของ OCR: การซ้ำวนลูป (repetition loop) ใน 112 ไฟล์ → re-OCR + merge + ตรวจสอบจนสะอาด
จุดที่โปรเจกต์รู้ตัวครั้งแรก นี่คือจุดที่รู้ว่า "คุณภาพ OCR เป็นปัญหาจริง ไม่ใช่ noise เล็กน้อยที่มองข้ามได้" — และนำไปสู่งานทั้งเฟส 3 ซึ่งกลายเป็นก้อนงานที่ใหญ่ที่สุดของโปรเจกต์

บทเรียนย่อยที่ได้: นามสกุล .dup ถูกใช้เป็น สัญญาณควบคุมของ pipeline อยู่แล้ว — เคยเผลอใช้ซ้ำเป็นนามสกุลไฟล์สำรอง ทำให้ pipeline สับสน อย่านำสัญญาณควบคุมที่มีความหมายอยู่แล้วไปใช้ซ้ำเพื่อจุดประสงค์อื่น

5เฟส 3 — ทำความสะอาด OCR (6–29 ก.ค.)

ก้อนงานที่ใหญ่ที่สุดและกินเวลามากที่สุด แบ่งเป็น 6 ชั้นตามลำดับที่ค่อยๆ ค้นพบ — แต่ละชั้นเกิดขึ้นเพราะชั้นก่อนหน้ามีจุดบอดที่มองไม่เห็นตอนสร้าง

5.1 ชั้นที่ 1 — scanner แบบ regex (6–7 ก.ค.)

scan_ocr_repetition.py ตรวจจับการซ้ำระดับ token ได้ดี แต่ต่อมาพบว่ามี ช่องโหว่เรื่อง intra-token repetition — การซ้ำที่เกิด ภายใน คำเดียว ซึ่ง regex ที่มองขอบเขตคำจับไม่ได้

5.2 ชั้นที่ 2 — LLM consensus scan (11–13 ก.ค.)

ปัญหาที่แท้จริงคือ OCR เสียแบบ "ไม่ซ้ำ แต่มั่ว" — ข้อความที่อ่านผ่านๆ ดูเหมือนภาษาไทยปกติแต่ไม่มีความหมาย ซึ่ง regex จับไม่ได้เลยไม่ว่าจะเขียนดีแค่ไหน จึงต้องใช้ LLM อ่านและตัดสิน

การทดลองที่ล้มแผนเดิมทั้งหมด แผนเดิมคือทำ cascade architecture — ให้โมเดลถูก/เร็ว (gemma) กรองชั้นแรก แล้วส่งเฉพาะที่ผ่านไปให้โมเดลแพง/แม่น (phi4) ยืนยัน ซึ่งเป็นสถาปัตยกรรมมาตรฐาน ที่ประหยัดต้นทุนที่สุด

แต่การทำ diff test ที่ระดับไฟล์ล้มมันทิ้ง — พบว่าโมเดลทั้งสอง flag คนละหน้ากันมากเกินกว่าที่จะเรียงชั้นได้ ถ้าใช้ cascade จริง สิ่งที่ gemma พลาดจะไม่มีวันถูก phi4 เห็นเลย จึงเปลี่ยนเป็น union scan (สแกนด้วยทั้งสองโมเดลเต็มรูปแบบ) แล้วใช้ AND gate (เอาเฉพาะหน้าที่ทั้งคู่เห็นตรงกัน) เพื่อคุมอัตราผลบวกลวง

บทเรียน: สถาปัตยกรรมที่ "ถูกต้องตามตำรา" อาจผิดกับข้อมูลจริง — และการทดสอบ ที่ระดับหน่วยงานจริง (ไฟล์) เผยสิ่งที่การทดสอบระดับย่อย (หน้า) มองไม่เห็น
ผลการสแกน สแกนครบ 2,853 ไฟล์ → flag 569 ไฟล์ ว่าน่าสงสัย

6.1 ทำไมต้อง tag entity

คำถามจริงที่ผู้ใช้ระบบนี้จะถามคือแบบ "อาจารย์ X ได้รับแต่งตั้งเมื่อไหร่" หรือ "หลักสูตร Y ผ่านมติครั้งไหนบ้าง" — ซึ่งต้องรู้ว่าเอกสารไหนพูดถึง entity ไหน ทั้งเพื่อทำ retrieval ที่ดีขึ้น และ (สำคัญกว่า) เพื่อ สร้างชุดคำถามทดสอบที่มีคำตอบถูกต้องแน่นอน

สำหรับ congen การป้อน context ยาวขึ้น ทำให้แย่ลง — เพราะ ConGen เป็น knowledge distillation แท้ๆ จาก teacher ที่ใช้กับคู่ประโยคสั้น การยืด input ไป 510 token จึงผลัก input ออกนอกการกระจายที่มันถูก distill มา = train/test mismatch ไม่ใช่ปัญหา truncation

สรุปเชิงปฏิบัติ: ใช้ 510 กับ sct, คง 128 กับ congen — และตัวเลข congen ทุกตัวในเอกสารเปรียบเทียบ (รวมถึงข้อสรุป "ผู้เชี่ยวชาญด้าน program") วัดที่ 128 ซึ่งการสอบสวนนี้ยืนยันว่าถูกต้องแล้ว ไม่ต้องแก้
ข้อสังเกตเชิงโครงสร้างสำหรับส่วน discussion ของเปเปอร์ embedder ไทยเฉพาะ ทุกตัวที่สำรวจมา (congen, sct, SimCSE-WangchanBERTa, ConGen-XLMR-Thai) สร้างบน RoBERTa/XLM-R base ซึ่งสืบทอดเพดาน position-embedding 512 token มาจากสถาปัตยกรรม BERT ดั้งเดิม — ไม่ใช่ความบังเอิญรายโมเดล แต่เป็นจุดตั้งต้นมาตรฐานของทุกทีมที่เทรน sentence embedder ไทย

ในทางกลับกัน bge-m3 (8,192 token) และ qwen3 (32k+) ที่ครองอันดับต้นในการเปรียบเทียบนี้ ไม่ได้มีภูมิคุ้มกันโดยธรรมชาติ — bge-m3 เองก็ใช้ XLM-R เป็นฐาน (ตระกูลเดียวกับโมเดลไทย) แต่ BAAI ลงทุนขยาย position embedding และ continued-pretrain สำหรับ long context โดยเฉพาะ

นัยต่อ RQ2: ช่องว่างคุณภาพส่วนหนึ่งที่วัดได้ อาจสะท้อน ช่องว่างด้านทรัพยากร/ความสุกงอมทางวิศวกรรมของระบบนิเวศ embedding ไทย ไม่ใช่ช่องว่างด้าน "ความเข้าใจภาษาไทย" — ซึ่งเป็นสองคำอธิบายที่มีนัยต่างกันมาก (อันหนึ่งบอกว่า "multilingual ดีกว่าสำหรับไทยโดยเนื้อแท้" อีกอันบอกว่า "โมเดลไทยยังไม่ได้รับการลงทุนรอบ long-context และอาจไล่ทันถ้ามีคนทำ")

แต่ผลของ congen ทำให้ต้องระวังไม่สรุปง่ายเกินไป — แม้จะมี context ให้ใช้มากขึ้น ระบอบการเทรนของโมเดลอาจทำให้การใช้มันกลับให้ผลเสีย กรอบที่ซื่อสัตย์คือ ข้อจำกัด 2 ชั้นที่ซ้อนกัน: (1) เพดานสถาปัตยกรรม 510 token ที่ไม่มีโมเดลไทยตัวไหนข้ามได้ และ (2) ภายในเพดานนั้น ความยาวที่ใช้ได้จริง ถูกกำหนดโดยระบอบการเทรน ไม่ใช่แค่สถาปัตยกรรม

7.3 วิธีทดสอบนัยสำคัญที่ใช้ตลอดโปรเจกต์

Holm-Bonferroni correction ใช้ แยกตามครอบครัวของการเปรียบเทียบที่เกิดพร้อมกัน ไม่รวมกันทั้งหมดเป็นก้อนเดียว — เช่น 36 คู่ของ embedder-vs-embedder เป็นหนึ่งครอบครัว ส่วน 9 คู่ของ BM25-vs-embedder เป็นอีกครอบครัวหนึ่ง เพราะการรวมทุกอย่างเป็นครอบครัวเดียวจะลงโทษหนักเกินจริงจนไม่พบผลอะไรเลย

7.4 ผลชุดแรก — "โมเดลเล็กเสมอโมเดลใหญ่"

ผลที่ยังยืนมาจนถึงวันนี้ โมเดลเล็กเสมอโมเดลใหญ่ ยืนยันใน 2 ตระกูลอิสระ: qwen3_0.6b เสมอ qwen3 (เล็กกว่า ~7 เท่า) และ e5_small เสมอ e5 (เล็กกว่า ~4.7 เท่า) — ทั้งคู่ Holm-adj p=1.0
สองตระกูลที่ไม่เกี่ยวกันให้ผลเดียวกัน = เป็น pattern จริง ไม่ใช่ฟลุ๊คของตระกูลเดียว

นัยเชิงต้นทุนสำหรับ RQ2: สมาชิกที่ถูกที่สุดของแต่ละตระกูลที่แข็งแรง เป็นตัวเลือกที่ดีกว่าพี่ใหญ่ของตัวเองเมื่อคิดต้นทุน โดยไม่มีการสูญเสียคุณภาพที่พิสูจน์ได้ — เป็นข้อสรุป RQ2 ที่คมและอ้างอิงได้มากกว่า "ใหญ่ที่สุดไม่ได้ชนะเสมอ"
อีกด้านหนึ่ง — โมเดลที่ควรเลิกใช้ sct เสมอ m2v ในทุก entity_type (Holm-adj p=1.0 ทุกช่อง) แม้จะแก้ max_seq_length แล้ว — sct ยังแยกไม่ออกทางสถิติจาก ตารางค้นหาเวกเตอร์แบบ static ที่ไม่ใช่ transformer เลย

7.7 BM25 — ผลที่พลิกกรอบคำถามวิจัยทั้งหมด

เพิ่ม BM25 เป็น lexical baseline เพราะโน้ตวิจัยกำหนดว่าต้องมีอย่างน้อย 1 ตัว "เพื่อทดสอบว่า dense embedding คุ้มหรือไม่" — แล้วพบว่า มันไม่ใช่ baseline อ่อนๆ อย่างที่ทุกคนคาด มันเสมอกับ dense tier บนสุด

สมมติฐานว่าทำไม BM25 ถึงแข็งขนาดนี้บนงานนี้ Gold query เป็น entity-anchored — ต่อให้เขียนถ้อยคำใหม่ให้ห่างจากชื่อเอกสารแค่ไหน ชื่อของ entity เองต้องคงอยู่ตรงตัว ไม่งั้นคำถามจะไม่ระบุว่าถามถึงมติไหน → ให้ความได้เปรียบเชิงโครงสร้างแก่การจับคู่คำตรงตัวบนงานนี้โดยเฉพาะ

นี่ไม่ใช่จุดอ่อนของการออกแบบ gold set แต่เป็นคุณสมบัติของโดเมน — คนถามเรื่องมติจริงๆ ก็จะระบุชื่อคน/หลักสูตรตรงตัวเช่นกัน

7.8 Hybrid (RRF) — ผลที่แข็งที่สุดในโปรเจกต์

ทฤษฎี — RRF (Reciprocal Rank Fusion) วิธีรวมผลลัพธ์จาก retriever หลายตัวโดย ใช้เฉพาะ "อันดับ" ไม่ใช้ "คะแนน" เอกสารหนึ่งได้คะแนนรวม = ผลรวมของ 1/(k + อันดับที่ได้จากแต่ละ retriever) โดย k=60 เป็นค่ามาตรฐาน

ข้อดีคือไม่ต้องปรับสเกลคะแนนจาก retriever ที่คิดคะแนนคนละแบบ (cosine กับ BM25 score เทียบกันตรงๆ ไม่ได้) และ เอกสารที่ BM25 จัดอันดับ 1 จะถูกคุ้มครองในผลรวมโดยโครงสร้าง — ข้อเท็จจริงนี้กลายเป็นกุญแจอธิบายผลของ reranker ในภายหลัง
ผลลัพธ์ Hybrid ชนะ dense อย่างเดียว 26 จาก 27 การทดสอบ (9 embedder × 3 metric) รวมถึงชนะแม้ในโมเดลที่ dense อ่อนมาก — เป็นผลที่แข็งที่สุดในการศึกษาทั้งหมด ตีความได้ว่าสัญญาณ lexical กับ dense เสริมกันจริง ไม่ใช่ซ้ำซ้อนกัน
แต่มี failure mode จริงที่ต้องระวัง m2v และ sct — hybrid แย่กว่า BM25 เปล่าๆ อย่างมีนัยสำคัญ
อย่า RRF กับ embedder ที่อ่อนโดยไม่คิด — สัญญาณ dense ที่อ่อนพอ จะลากผลรวมลง ไม่ใช่ทุกการ fuse จะปลอดภัย

7.9 ต้นทุนและความหน่วง — พบ overhead ที่ซ่อนอยู่

วัด latency แล้วพบว่า implementation ปัจจุบันของ HybridRetriever และ BM25Retriever (ดึงทั้งคอร์ปัส k=n ก่อน fuse และสร้าง BM25Okapi ขึ้นใหม่ทุก query) เพิ่ม overhead คงที่ ~1.9–2.0 วินาทีต่อ query แทบไม่ขึ้นกับ embedder ที่ใช้เลย เพราะมันสเกลตามขนาดคอร์ปัส ไม่ใช่มิติของ embedding

รายงานตามจริง ไม่แอบแก้ ตัวเลข ~2.1–2.7 วินาทีที่วัดได้ ส่วนใหญ่คือ overhead ที่หลีกเลี่ยงได้ ไม่ใช่ต้นทุนของ RRF เอง (ต้นทุนแท้จริงอยู่ที่ ~116–668 มิลลิวินาที)
เมื่อแสดงเป็นอัตราส่วนจะดูน่าตกใจ (~4 เท่าสำหรับ embedder ที่แพงที่สุด ถึง ~18 เท่า สำหรับตัวที่ถูกที่สุด) แต่นั่นเป็นเพราะเอา overhead คงที่ตัวเดียวกันไปหาร ด้วยฐานที่ต่างกันมาก — ตัวเลขแบบบวก (~2 วินาที) คือเรื่องจริง

รายงานไว้เป็น คุณลักษณะของ implementation ไม่ได้แอบแก้ระหว่างวัด เพราะการแก้ระหว่างทางจะทำให้ตัวเลขก่อน/หลังเทียบกันไม่ได้

คำอธิบายจากวรรณกรรมจริง

สิ่งนี้ไม่ได้เดาจากข้อมูลของเราเอง — มีการค้นวรรณกรรม IR ปฐมภูมิเป็นงานแยกต่างหาก:

  1. ประโยชน์ของ reranking ลดลงเมื่อ retriever ชั้นแรกแข็งขึ้น และพลิกเป็นโทษได้ — Rosa et al. (arXiv:2212.06121) แสดงว่า monoT5 ยก BM25 (+0.055 nDCG@10) และ dense ที่แข็งกว่า (+0.045) ขึ้นสู่เพดานเดียวกัน คือได้กำไรน้อยลงเมื่อฐานแข็งขึ้น ส่วน Jacob et al. (ReNeuIR 2025 @ SIGIR, arXiv:2411.11767) ให้ตัวอย่างที่พลิกเป็นลบ โดยระบุ bge-reranker-v2-m3 ตรงรุ่นที่เราใช้ ว่า "มักทำได้แย่กว่า retriever" และตั้งชื่อ failure mode ว่า "phantom hits" — ให้คะแนนสูงอย่างมั่นใจ กับเอกสารที่ไม่มีความเกี่ยวข้องทั้งเชิงคำและเชิงความหมายกับ query เลย
  2. RRF ปกป้องสัญญาณ exact-lexical-match เชิงโครงสร้าง — Cormack et al. (SIGIR 2009) นิยาม RRF ว่ารวม "อันดับโดยไม่สนใจคะแนนที่ตามอำเภอใจของแต่ละวิธี" เอกสารที่ BM25 จัดอันดับ 1 จากการจับคู่คำตรงตัวจึงถูกคุ้มครองโดยการออกแบบ ส่วน cross-encoder ที่เห็นแค่คู่ (query, chunk) มองไม่เห็นเลยว่า candidate นี้มาจากขาไหนหรือเพราะอะไร
    (หมายเหตุ: เปเปอร์ปี 2009 เกิดก่อน dense retrieval และไม่เคยพูดถึงการ fuse lexical+dense หรือ reranker — การเชื่อมโยงนี้เป็นการอนุมาน เชิงสถาปัตยกรรมของโปรเจกต์นี้เอง ไม่ใช่ข้อกล่าวอ้างของเปเปอร์)
  3. reranker สำเร็จรูปอาจไม่ transfer ไปยัง candidate distribution แบบ hybrid — HYRR (Google Research, arXiv:2212.10528) ให้เหตุผลว่าทำไมต้องเทรน reranker บน candidate ของ hybrid โดยเฉพาะ และ training mixture สาธารณะของ bge-reranker-v2-m3 ไม่มีองค์ประกอบที่มาจาก hybrid เลย
  4. ไม่มีเปเปอร์ไหนทดสอบไปป์ไลน์ตรงกับของเรา (RRF hybrid → bge-reranker-v2-m3) — นี่เป็น data point ใหม่จริง ไม่ใช่การทำซ้ำผลที่มีคนรายงานแล้ว

9.2 thematic query กลับมามีความหมาย (30 ก.ค.)

ย้อนไปดูสาเหตุว่าทำไม 179 thematic query (§6.4) ถึงแทบไม่มีอำนาจจำแนก chunker เลย (t=0.02) แล้วพบต้นตอที่ไม่เคยสังเกตมาก่อน: คำถามทั้ง 179 ข้อถูกออกแบบให้ผูกกับ การประชุมครั้งใดครั้งหนึ่งโดยเฉพาะ แต่ไม่มีข้อไหนเลยระบุชื่อการประชุมนั้นในตัวคำถาม (เขียนแค่ "ในการประชุมครั้งนี้") — คำถามจึงตอบไม่ได้จริงตั้งแต่ถูกสร้าง ไม่ใช่ว่า chunker หรือ embedder แยกแยะไม่ออก

แก้ไขแล้ว — และพลิกเป็นสัญญาณคนละทิศกับที่คาด tools/eval/qualify_thematic_queries.py เขียนคำถามทั้ง 179 ข้อใหม่ให้ระบุ ชื่อการประชุม แล้ว re-evaluate ด้วย run_thematic_eval.py — เหตุผลที่ยังต้อง แยกชุดนี้ออกจาก entity-anchored set อยู่ดี เปลี่ยนไปจากเดิม: แต่ก่อนคือ "เจือจาง" ตอนนี้คือ "ชี้ไปคนละทาง" — chunker-axis กลับหัว (fixed_size − semantic = +0.0256 บน thematic เทียบกับ −0.0359 บน entity-anchored; semantic เป็น chunker แย่ที่สุดบน thematic แต่ดีที่สุดบน entity-anchored) การนำสองชุดมาเฉลี่ยรวมจะหักล้างผลจริงสองอันเข้าด้วยกัน ไม่ใช่แค่เจือจางผลอันเดียว ยังคงมีอำนาจทดสอบต่ำต่อคู่ (2/27 มีนัยสำคัญ, เสมอกัน 62%) — อ้างเป็น query shape แยกต่างหาก ห้ามเฉลี่ยรวม

9.3 กฎ RRF ที่วัดครบทั้งสองทิศ — "hybrid ชนะเสมอ" คือ finding เฉพาะ entity-anchored

เมื่อ thematic query กลับมาใช้ได้จริง จึงรัน BM25/hybrid significance test บนมันเป็นครั้งแรก (hybrid_significance_test_9way.py --thematic) แล้วพบว่า ผลนี้พลิกข้อสรุปที่แข็งที่สุดของโปรเจกต์ (§7.8) และใหญ่กว่าที่คาด

"hybrid ชนะ dense ทุก embedder" ไม่เป็นจริงบน thematic BM25 อ่อนบน thematic (0.2988) เทียบกับ entity-anchored (0.4930) — เพราะไม่มีชื่อ entity ให้จับคู่ตรงตัว บน thematic recall@10: ชนะอย่างมีนัยสำคัญแค่ 3 · เสมอ 4 · แพ้อย่างมีนัยสำคัญ 2 (e5 −0.0445, qwen3 −0.0526) และส่วนต่าง hybrid−dense เป็นฟังก์ชันโมโนโทนิกกับความแข็งของ dense เอง (r = −0.925) โดยพลิกเครื่องหมายพอดีที่คะแนนของ BM25 เอง
กฎทั่วไปที่วัดแล้วทั้งสองทิศ — ครอบคลุมกรณี m2v/sct เดิมด้วย RRF ช่วยแขนที่อ่อนกว่า และเก็บภาษีจากแขนที่แข็งกว่า — fuse เมื่อสองแขนสูสีกันเท่านั้น ไม่ว่าแขนไหนจะเป็นฝ่ายอ่อน นี่คือกรอบเดียวที่อธิบายทั้งกรณีเดิม (m2v/sct ที่ dense อ่อนกว่า BM25 มาก → hybrid แย่ลง) และกรณีใหม่นี้ (dense แข็งกว่า BM25 มาก บน thematic → hybrid ก็แย่ลงเหมือนกัน) ด้วยกลไกเดียว

9.7.1 Statistical power — ปิดแล้ว

tools/eval/power_analysis.py 138 จาก 180 คู่เปรียบเทียบมีนัยสำคัญ และทั้ง 42 คู่ที่เสมอ มี |diff| จริง ต่ำกว่า MDE (Minimum Detectable Effect) ของมันเอง — ไม่มีคู่ไหนในนี้เป็นแค่ "power ไม่พอ" ทุกคู่อ้างเป็นขอบเขตได้จริง (ดู [[feedback_report_ties_as_bounds]]) chunker tie แคบที่สุด (ตัดความต่าง recall@10 >0.031 ออกได้แล้ว) ส่วน embedder tie กว้างกว่า (0.05–0.10) — คู่เดียวที่ต้องเรียกว่า "สรุปไม่ได้" จริงๆ คือ e5_small vs jina_v5 บน MRR (ขอบเขต 0.1045) รูปแบบปิด (closed-form) ตรวจสอบกับ bootstrap จำลองจริงแล้วตรงกัน (power จริง 0.78–0.86 เทียบเป้า 0.80)

9.7.2 Pooling bias — ประเด็นที่ใหญ่ที่สุด ปิดด้วยการแก้ตัวเองกลางทาง (30 ก.ค.–3 ส.ค.)

qrels ของโปรเจกต์นี้สร้างจาก string containment — วิธีเดียวกับที่ BM25 ใช้ค้น — เอกสารที่เกี่ยวข้องจริงแต่ใช้ถ้อยคำต่างออกไป (หรือชื่อถูกตัดจาก OCR) จะกลายเป็น false negative ที่ลงโทษ dense retrieval สำหรับการตอบถูก ชี้ตรงไปที่ข้อสรุป "BM25 ชนะ bge_m3" และ "BM25 แบก person (0.8147)" (§9.3, §7.6)

9.8 RQ4 — คุณภาพคำตอบปลายทาง (30 ก.ค.–3 ส.ค., COMPLETE)

คำถามวิจัยข้อสุดท้ายที่ยังไม่เริ่ม และเป็นตัวเดียวที่ไม่ถูกบล็อกโดยการ rebuild ที่ค้างอยู่ (context มาจากผลการค้นที่ persist ไว้แล้ว ไม่ต้องใช้ GPU ใหม่) รูปแบบ: 5 อาร์ม × 106 query = 530 การ generate ด้วย phi4 รันบนเครื่อง เท่านั้น (ไม่ใช้ API ภายนอก) วัดด้วย metric เชิงวัตถุ (citation precision/recall, unsupported-citation rate, abstention correctness) ไม่ใช้ LLM ตัดสินคุณภาพคำตอบ

บั๊กที่พบระหว่างสร้าง — เงียบและอันตราย Ollama ตัด prompt ที่ยาวเกิน num_ctx จากด้านหน้า โดยไม่มีคำเตือน — ค่า default 4096 จึงลบคำสั่งของ prompt ทิ้งเงียบๆ เมื่อ context ยาว ได้คำตอบที่ลื่นไหล น่าเชื่อ แต่ไม่มีการอ้างอิงเลยสักคำ แก้ด้วยการตั้ง num_ctx เอง + วาง instruction หลัง context เสมอ
ผลสุดท้าย (หลังทำ ablation เพื่อแก้ข้อสรุปที่เขียนผิดรอบแรก) Citation precision เรียงลำดับตรงกับ recall@10 เป๊ะ (hybrid > dense > bm25 > m2v) — คุณภาพการค้นรอดมาถึงขั้นตอนสร้างคำตอบ arm-ordering ทดสอบนัยสำคัญแล้ว: hybrid/dense/bm25 เป็นกลุ่มบนที่เสมอกันเป็นส่วนใหญ่ (hybrid-vs-bm25 ยังแยกกันได้) ส่วน m2v แพ้ทั้งสามอย่างมีนัยสำคัญทั้ง precision และ recall

0 การอ้างอิงที่กุขึ้นมาเอง จากทั้งหมด 978 ครั้ง — failure mode ที่ RAG กลัวที่สุด ไม่เกิดขึ้นเลยในงานนี้ ซึ่งเป็นผลตอบแทนของการใช้ label ตัวเลขที่ตรวจสอบได้ชัดเจน ([1]..[k] ไม่ใช่ resolution_id เต็ม)
ข้อสรุปที่เขียนผิดรอบแรก แล้วแก้เองในวันเดียวกัน Citation recall แบนราบที่ ~0.41 ทุกอาร์ม ไม่ว่าจะมีมติถูกอยู่ในบริบทกี่ฉบับ — เขียนไว้รอบแรกว่า "ตัวสร้างคำตอบ (generator) คือคอขวด" แต่ตรวจดูให้ละเอียดพบว่า จำนวนการอ้างอิงต่อคำตอบคงที่ที่ค่าเฉลี่ย 2.65 / median 2 ไม่ว่าจะมีมติถูกให้อ้างกี่ฉบับ และ recall ยิ่งลดลงเมื่อมีมติถูกมากขึ้น (0.778 ที่มี 2 ฉบับ → 0.381 ที่มี 5+ ฉบับ) — เป็นลายเซ็นของงบประมาณคงที่ที่ prompt กำหนดไว้ ไม่ใช่ขีดจำกัดของโมเดล: กติกาข้อ 4 ของ prompt เขียนว่า "ตอบสั้น ๆ ไม่เกิน 3 ประโยค" ขณะที่ gold set ส่วนใหญ่เป็นคำถามแบบรวบยอด (เฉลี่ย 9.87 มติถูกต่อคำถาม) — สองสิ่งนี้ชนกันเอง
ยืนยันด้วย ablation จริง ไม่ใช่แค่อนุมาน — คำแนะนำพลิกตามที่ทำนายไว้ รัน hybrid + BM25 ซ้ำ (212 gen) โดยแทนกติกาข้อ 4 ด้วย "อ้างอิงมติที่เกี่ยวข้องทุกฉบับ" (cite_all) ผล: citation recall ขึ้นอย่างมีนัยสำคัญทั้งสองอาร์ม (hybrid 0.2862→0.3865, bm25 0.2127→0.3034, Holm-adj p<0.0001 ทั้งคู่) โดย precision ไม่เปลี่ยนแปลงอย่างมีนัยสำคัญ — แปลว่าโมเดลไม่ได้อ้างมั่วขึ้น มันแค่อ้างถูกมากขึ้นจริง คำแนะนำพลิกตามที่ทำนายไว้: นี่คือปัญหาที่ prompt ไม่ใช่ข้อจำกัดของ phi4

ขยายผลอีก 3 อาร์ม (dense/m2v/closed-book) ภายใต้ cite_all จนครบตาราง 5 อาร์ม × 2 prompt พบว่า กำไรจาก recall ไม่เป็นสากล — มีนัยสำคัญสำหรับ hybrid/dense/bm25 แต่ไม่มีนัยสำคัญสำหรับ m2v (+0.026, p=0.657) สอดคล้องกับ คุณภาพการค้นที่อ่อนอยู่แล้ว (ไม่มีหลักฐานถูกพอในบริบทให้อ้างเพิ่ม ไม่ว่า prompt จะสั่งอย่างไร) และ arm-ordering ยิ่งคมขึ้นภายใต้ cite_all (8/12 คู่มีนัยสำคัญ เทียบ 6/12 ภายใต้ prompt เดิม)
ต้นทุนเล็กๆ ที่เจอเมื่อเปลี่ยน prompt closed-book abstention ตกจาก 106/106 → 104/106 ภายใต้ cite_all (hallucination 2 ครั้ง, phantom citation 5 ครั้ง จาก 5) — คำสั่ง "อ้างอิงทุกฉบับ" ไม่มี guard กันกรณีไม่มีเอกสารเลย ต้องปรับถ้อยคำก่อนใช้ cite_all เป็น prompt สุดท้ายของเปเปอร์

ไม่ช่วย — ทำให้ hybrid MRR แย่ลงอย่างมีนัยสำคัญ (0.7775 → 0.6775) และมีต้นทุน ~1.17 วินาทีต่อ query; กับ dense เปล่าๆ ไม่มีผลทั้งสองทิศทาง มีวรรณกรรมรองรับ (โมเดลรุ่นเดียวกันเป๊ะ)
ยังไม่ได้ทดสอบ: reranker ที่เทรนบน candidate แบบ hybrid โดยเฉพาะ หรือการผสมคะแนน reranker เข้าไปใน RRF เป็นสัญญาณที่ 4 แทนการตัดทิ้งแล้วแทนที่ — เป็นสมมติฐาน ไม่ใช่ผลการทดลอง

Q6. preprocessing แบบไทยๆ ช่วยไหม? (RQ3)

12บทเรียนเชิงกระบวนการ

1. หลัง rebuild index ต้อง refresh ทุก เส้นทาง retrieval ที่มีผล persist ไว้

ไม่ใช่แค่ตัวที่ eval script บังเอิญคำนวณใหม่ให้เอง — บั๊กนี้เกิดซ้ำ 5 ครั้ง ในไฟล์ต่างกัน (BM25, hybrid, cost_latency, multi_k, reranker, entity_boost/lookup)
วิธีตรวจ: เทียบ mtime ของ data/results/* กับเวลา rebuild ก่อนเชื่อ significance test ใดๆ

2. ตัวเลขดิบไม่ใช่ finding จนกว่าจะถูกทดสอบ

"semantic ชนะ", "bge-m3 แซง qwen3", "top combo 0.7048" — ทั้งสามตายเมื่อถูกทดสอบ หรือถูกวัดใหม่ ทุกอันเคยถูกเขียนซ้ำในเอกสารหลายรอบ เพราะไม่มีใครถามว่า "ทดสอบหรือยัง" — คำถามนี้ควรถามทุกครั้งที่จะเขียน ตัวเลขเปรียบเทียบลงเอกสาร

3. สแกนถูกๆ ทั้งคอร์ปัสก่อน แล้วค่อยลงทุน GPU

ก่อนแก้ regex กว้างๆ หรือรัน pilot บน GPU ให้รันสแกนถูกๆ เพื่อวัดขนาดปัญหาจริง และลองแก้แบบไร้เดียงสากับข้อมูลจริงดูก่อน — ยืนยันคุณค่าไปแล้ว 2 ครั้งภายในวันเดียว

4. เมื่อ heuristic พลาดเคสที่รู้ว่าจริง ให้เช็คก่อนว่าข้อมูลมี field ระบุตำแหน่งอยู่แล้วหรือยัง

(เช่น span) แทนที่จะประดิษฐ์ heuristic ตัวใหม่ขึ้นมาอีก — และให้ลอง reframe ด้วยว่า ขั้นตอนก่อนหน้าอาจเป็นตัวกรอง "ต้นทุน" ไม่ใช่ตัวกรอง "คุณภาพ" ซึ่งเปลี่ยนวิธีคิดเรื่องสิ่งที่มันคัดทิ้งไปโดยสิ้นเชิง

5. อย่าประมาณเวลาที่เหลือของงาน GPU จาก batch แรกๆ

sentence-transformers เรียง batch ที่ยาวที่สุดขึ้นก่อน และจ่ายค่า CUDA warm-up ครั้งเดียวตอนเริ่ม → batch แรกๆ ช้าผิดปกติเสมอ เคยฆ่า job ที่กำลังทำงานปกติดีทิ้งเพราะตกใจกับ ETA ที่คำนวณจากตรงนั้น

6. ออกแบบการทดลองให้ isolate ตัวแปรจริงๆ

reranker baseline = slice ของ pool ตัวเอง · ConGen/SCT = backbone + teacher เดียวกัน ต่างแค่วิธีเทรน · ปฏิเสธ SimCSE-WangchanBERTa เพราะจะเปลี่ยน 2 ตัวแปรพร้อมกัน · ปฏิเสธ Qwen3-8B เพราะ quantization จะเพิ่มตัวแปรใหม่ซ้อนตัวแปรที่ต้องการวัด

7. รายงานผลลบและข้อบกพร่องของ implementation ตามจริง

reranker ให้ผลลบ → รายงาน + ไปหาวรรณกรรมรองรับ · hybrid มี overhead 2 วินาที → รายงานไว้ตรงๆ ไม่แอบแก้ระหว่างวัด · pipeline OCR ไม่มี ground truth → บอกให้ผู้ใช้รู้ก่อนอนุมัติ
