## Status 2026-08-08 — the 4 mispairings are APPLIED; flag count 7 → 3

Applied by `tools/corpus_prep/fix_manifest_title_mispairings.py --apply`, then
propagated to built artifacts by `tools/corpus_prep/relabel_renamed_resolution_ids.py`.

**It was a relabel, not a rebuild — the premise this waited on was wrong.** The
plan recorded here for a week was to let these ride "the rebuild after #3",
because 4 of them move a `resolution_id`. But a title change moves an id without
changing a single chunk of *text*, and embeddings are a function of text alone,
so the correct operation is a rename of two columns: no GPU, no re-embedding, and
rewriting a persisted result is exactly equivalent to re-running retrieval against
the relabelled index. Cost was minutes, not the ~16.4 h a rebuild would have
taken. Nothing was waiting on the rebuild except the belief that it was needed.

What was changed:

* **4 manifest titles**, in 3 meetings. `file` and `url` were deliberately left
  alone: for the `2565/ครั้งที่ 8` swap all three fields are internally consistent
  and it is the *downloaded content* that landed in the other entry's file, so
  swapping titles is the single edit that re-aligns title, body **and** url at
  once. Swapping `url` would fix the source and leave the text wrong; swapping
  `file` would fix the text and leave the url wrong.
* **Replacement titles are each file's own stem, whitespace-collapsed** — never a
  title reconstructed from the body, which would encode metadata that exists in
  no source (ADR-0003). Two stems end mid-word (`... เป`, `... บูรณ`) because the
  download truncates long filenames; the audit's asymmetric coverage scores those
  1.00 by design.
* **41 of 55 indices** (2,021 rows) and **302 of 24,217 persisted result files**
  (323 rows) relabelled. Only `chunks.parquet` carries ids — `lexical.json` and
  `embeddings.npy` are row-aligned, and `meta.json`/`manifest.json` describe the
  combo, not its documents. The other 14 indices are the toy smoke builds.

**No metric can have moved.** Neither the 4 old ids nor the 4 new ones appear in
either gold query set — 0 references against a denominator of 358 `resolution_id`
entries, printed with the denominator on purpose, because "0 affected" is
otherwise ambiguous between "checked and clean" and "the pattern could never have
matched".

Verification, in the order it was run:

1. The id mapping was **derived, not typed**: `resolution_id` snapshots taken
   with the real loader either side of the manifest edit, diffed. Exactly 4 ids
   moved, 0 duplicates corpus-wide afterwards.
2. `audit_resolution_ids.py` — unchanged: the same 2 reviewed-and-accepted
   clashes, every id unique after the `#N` rank.
3. **Text-level check, which is the one that matters**: a swap applied the wrong
   way round yields exactly the right set of ids with exactly the right row
   counts, so counting proves nothing. All 4 new ids were verified against the
   full text of the file that now carries them — 9/9, 12/12, 16/16, 12/12 chunks
   found in the right source file, `chunk_id` consistent with
   `<resolution_id>:<chunk_index>` throughout.
4. The 2 genuinely retired ids are gone: **0 rows of 2,710,194** across 55
   indices, **0 of 24,217** result files.
5. `audit_pipeline_invariants.py` — **24 pass / 0 warn / 1 fail**, unchanged, the
   single FAIL being the known `BuildCombo.id` caveat. `E3a` at 0 of 23,156 live
   result files is the mechanical confirmation that index and results were
   relabelled consistently.
6. `audit_title_body_agreement.py` — **7 flagged → 3**, and the 3 are exactly the
   ones deliberately kept (2 never-fetched, 1 generic container title). Median
   1.000 unchanged, mean 0.896 → 0.898.
7. `audit_doc_claims.py` — 3 pass / 2 warn / 0 fail, both warns the known
   by-design ones.

**Two lessons this repair produced, both now encoded in code rather than prose.**

* A **swap is not idempotent**: re-running the relabel would swap the pair back.
  The script's guard — refusing when a new id already sits on rows it is not
  relabelling — catches that, and did, on the verification re-run. A second apply
  now fails loudly instead of silently reverting the repair.
* **`I6` could not see this change at all.** `audit_pipeline_invariants.py`
  computed "the corpus's last edit" from `*.md` mtimes only, but a
  `resolution_id` comes from `meeting_manifest.json` (ADR-0003) — so a title
  repair moves ids without touching one `.md`, and I6 would have reported all 41
  affected indices as current while they still held pre-repair ids: a stale index
  passing the check written to catch stale indexes. I6 now also reads manifest
  mtimes, and counts a recorded relabel (`relabeled_mispairings.at` in the index
  manifest) as bringing an index current without a rebuild — otherwise every
  index would stay permanently warned after any title repair, and a check that is
  always red is one nobody reads.

Still open, tracked separately: the **2 never-fetched documents** in
`2564/ครั้งที่ 12`, which are the same shape as `2568/ครั้งที่ 7`'s CHECO defect
(correct Drive id `1d4iz1dpnPweAn7pxBfxlvJf9IJZwIJFJ`, never fetched). That makes
**3 URLs** owed to one re-download + re-OCR pass, not 1. 0 gold queries cite any
of them.
