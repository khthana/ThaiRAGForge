## Decisions so far

- [fine-tune embedding model เขาทำกันยังไง + RTX 3060 12GB ทำได้แค่ไหน](issues/03-how-finetuning-works.md) — **12GB พอ โดยไม่ต้อง quantize** (bf16 + LoRA r=16–32 + gradient checkpointing + CachedMNRL); full FT เกินงบ ~5.5 เท่า เป็นไปไม่ได้ ผลที่คาดได้จริงจากวรรณกรรมที่มีเลขสัมบูรณ์ = **+0.03..+0.07 recall@10 บน dense-alone** และยัง**ไม่มีใครวัด**ว่ามันโอนเข้า hybrid เท่าไร ความเสี่ยงที่ใหญ่กว่า VRAM คือ **train/inference length mismatch** (เทรนได้ 256–512 tok แต่ chunk ยาวถึง 3,116 tok — repo นี้มีหลักฐานในบ้านแล้วว่า congen เจ๊งด้วยเหตุนี้ −0.0298, p=0.0016) ทางที่ถูกกว่ามาก: **linear query adapter** (ไม่ต้อง re-index เลย, เทรนเป็นนาที) เวลาเทรน 4B ≈ 6–9 ชม./epoch, 0.6B ≈ 1–1.5 ชม.
- [dataset สำหรับ fine-tune ภาษาไทย หาจากไหน — และ silver set ของเราใช้ได้มั้ย](issues/04-where-to-get-training-data.md) — ชุดสาธารณะไทย**ไกลโดเมนสามชั้น** และ repo นี้**มีหลักฐานในบ้านค้านอยู่แล้ว** (`sct` เทรนบน scb-mt ได้ recall@10 0.1519 แพ้ BM25 −0.4158) ยกเว้น **`WangchanX-Legal-ThaiCCL-RAG`** (8,211 คู่, MIT, ภาษากฎหมายไทย, มี hard negative มาให้) ที่ใกล้ทะเบียนภาษาราชการที่สุด **Silver ห้ามใช้เป็นสัญญาณหลัก** (สอน lexical overlap = เลียนแบบ BM25 แทนที่จะเสริม) ใช้ฟรีได้เฉพาะเป็นแหล่ง positive สำหรับขุด negative + sanity check ทางหลักคือ**สังเคราะห์ ~7,100 คู่จาก 2,372 มติ** (หัก 481 resolution_id ของ Gold = 16.86% ของคลัง) ด้วย Typhoon บน Ollama ต้นทุน ~2–3 วันเครื่อง **ความเสี่ยงที่ลดไม่ได้: มติพี่น้องที่หน้าตาเหมือนกันจะทำให้ Gold 73 หลัง fine-tune ประเมินสูงเกินจริงโดยตรวจไม่ได้**

- [73 คำถามพิสูจน์ได้แค่ไหน — effect size ที่เล็กที่สุดที่จะ significant](issues/05-what-can-73-queries-prove.md) — **+0.03..+0.04 พิสูจน์ไม่ได้** และไม่ใช่แค่ในการจำลอง แต่**เกิดขึ้นจริงแล้ว**: `semantic×qwen3_0.6b` ชนะ `semantic×congen` ที่ +0.0282 ได้ p=0.1054 และชนะ `sentence×qwen3_0.6b` ที่ +0.0381 ได้ p=0.1182 — ทั้งคู่ยังไม่ผ่าน Holm ด้วยซ้ำ สาเหตุคือ **churn จริง ≈ 0.72** (ทุก 4 คำถามที่ดีขึ้น มี ~3 คำถามแย่ลง วัดจากคู่ระบบจริง 6 คู่) ที่ churn ระดับนี้ Δ=+0.035 ให้ power เพียง **~0.11** MDE ที่แท้จริงไม่ใช่ตัวเลข Δ แต่คือ **จำนวนคำถามที่เปลี่ยนแบบไม่มีตัวถ่วง** (≥4 คำถาม) โครงสร้าง gold ซ้ำเติม: median 7 มติ/คำถาม สูงสุด 43 → พลิก 1 มติขยับ mean recall ได้ตั้งแต่ +0.0068 ถึงแค่ +0.0003 **ผลตรง: เกณฑ์ข้อ 4 ของตั๋ว 08 ตก → no-go ถ้ายังยึดเกณฑ์เดิม** เพิ่มเติม: ชุดคำถามนี้ลงโทษ churn **แบบไม่สมมาตร 1.84 เท่า** (ก้อนที่ยังไม่เจอมีมูลค่าเฉลี่ย 0.0774 แต่ก้อนที่เจอแล้วมูลค่า 0.1426) → ระบบที่พลิกก้อนแบบสุ่มที่ churn 0.75 ได้ผลสุทธิ **ติดลบ** และถ้าจะพิสูจน์ Δ=+0.03 ให้ได้ power 0.8 ต้องใช้ **~250–300 คำถาม** ไม่ใช่ 150

## Not yet specified

หมอกที่มองเห็นแล้วแต่ยังคมไม่พอจะตั้งเป็นตั๋ว — จะแปลงเป็นตั๋วเมื่อแนวหน้าคืบไปถึง:

- **Linear query adapter** (Chroma-style) — ตั๋ว 03 §5.1 ชี้ว่าเป็นทางที่คุ้มที่สุดในรายการ: ไม่ต้อง re-embed 81,489 chunks เลย ใช้ข้อมูลน้อยถึง 1,500 คู่ เทรนเป็นนาที เข้ากับ hybrid ทันที **แต่เลขที่อ้างเป็นเปอร์เซ็นต์สัมพัทธ์บน benchmark อังกฤษ และรายงานเองว่า gain ข้ามภาษาอ่อนกว่ามาก** — จะกลายเป็นตั๋วเมื่อ 09 บอกว่ามีสัญญาณพอ
- **Metadata pre-filter / query understanding** — มี `meeting_manifest.json` (ปี/ครั้งที่/เรื่อง/URL) + NER entities อยู่แล้วแต่ยังไม่ได้ใช้กรองก่อน retrieve ประโยชน์ขึ้นกับว่าคำถามจริงของสภาวิชาการมีตัวกรองชัดแค่ไหน (ตั๋ว 02)
- **การไปขอต้นฉบับที่คุณภาพดีกว่า** — วงจรป้อนกลับ: OCR พังเป็นเพดานของ recall → ต้นฉบับดีกว่ายกเพดานให้ทุกวิธี → แต่ต้องมีเดโมก่อนถึงจะได้ความร่วมมือ ขนาดของผลขึ้นกับตั๋ว 01
- **โครงสร้าง eval ของคำตอบ (ไม่ใช่ของ retrieval)** — LLM judge? เกณฑ์ให้คะแนนแบบมือ? กี่คำถามถึงพอ? รอนิยาม "ถูก/มั่ว" จากตั๋ว 06
- **การแก้ overhead 2.1–2.3 วินาทีต่อ query** — รู้สาเหตุแล้ว (BM25Okapi สร้างใหม่ทุก query, hybrid ดึง k=n ทั้ง corpus ก่อน fuse) เป็นงานวิศวกรรมล้วน ไม่ใช่การตัดสินใจ — จะกลายเป็นตั๋วก็ต่อเมื่อพบว่าความเร็วมีผลต่อ wow จริง
- **บทเดโม / UI / การจัดฉาก** — ถามอะไรตามลำดับไหน แสดงการอ้างอิงยังไง ทำอะไรตอนระบบไม่รู้คำตอบ
- **ผลของการเก็บผลลัพธ์แค่ top-10** — ไฟล์ผลต่อคำถามใน `data/results/gold_hybrid_73det/` เก็บไว้แค่ `rank ≤ 10` (ตรวจแล้ว 2026-07-31) แปลว่าคำถามสำคัญของตั๋ว 01 ที่ว่า "มติที่พลาดไปอยู่อันดับ 11–50 หรือไม่ติดเลย" **ตอบจากข้อมูลที่มีไม่ได้** ต้องรัน retrieval ใหม่ที่ k=50 (ใช้ GPU, หลักชั่วโมง) — **และการวัดที่งบเท่ากัน (2026-07-31) ทำให้มันคุ้มขึ้นมาก ไม่ใช่น้อยลง**: หลักฐานชี้ว่าความลึกให้ผลมากกว่าความหลากหลาย แต่เราวัดผลของความลึกไม่ได้เลยเพราะไฟล์ตัดที่ 10 — k=50 จะตอบทั้ง "ก้อน B อยู่ไหน" และ "recall@20/@50 ของระบบเดียวเป็นเท่าไหร่" ซึ่งเป็นคู่เทียบที่ตั๋ว 12 ขาดอยู่
- **จำนวนเอกสารที่ส่งให้ LLM ควรเป็นเท่าไหร่** — ทุกตัวเลขในแผนที่นี้ตรึงไว้ที่ 10 ใบโดยไม่มีใครตั้งคำถาม แต่ Qwen3 มี ctx 32K และ union 2 ระบบที่ 20 ใบให้ recall 0.8130 ทันทีโดยไม่ต้องมี router เลย **ยังไม่มีใครวัดว่า LLM ตอบแย่ลงมั้ยเมื่อได้ 20 ใบแทน 10** (สัญญาณรบกวนมากขึ้น → เสี่ยงมั่วมากขึ้น ซึ่งเป็นข้อจำกัด ข. ของปลายทาง) — จะกลายเป็นตั๋วเมื่อตั๋ว 06 นิยาม "ถูก/มั่ว" เสร็จ
- **กฎที่ควรใช้กับทุกตัวเลขต่อจากนี้** — การเทียบใด ๆ ต้องระบุ **จำนวนเอกสารที่ดึง** เสมอ รอบนี้เกือบรายงานผิดเพราะนับ "ดึงเยอะขึ้น" เป็น "ฉลาดขึ้น"

## Out of scope

- **การสร้างระบบจริง** — ผู้ใช้เลือกโหมด "วางแผนอย่างเดียว" (2026-07-31) ตั๋วทุกใบจบที่การตัดสินใจ งานสร้างเปิดเป็นแผนที่ใบใหม่หลังใบนี้จบ
- **RQ4 เต็มรูปแบบเป็นแขนวิจัย** — การวัดคุณภาพคำตอบปลายทางอย่างเป็นระบบเพื่อตีพิมพ์ เป็นเปเปอร์คนละใบ แผนที่นี้แตะแค่เท่าที่จำเป็นต่อการตัดสินว่าเดโม wow หรือไม่
- **Group D commercial API embedders** (OpenAI / Cohere / Gemini) — ตัดออกไปแล้วตั้งแต่เปเปอร์แรก ด้วยเหตุผล data egress ของเอกสารสถาบัน เหตุผลนั้นยังใช้ได้กับเดโม
- **งานเก็บกวาดของเปเปอร์แรก** (per-chunker significance test ที่ค้าง, multi-k rerun) — เป็นงานของ RQ1/RQ2 ไม่ใช่เส้นทางสู่เดโม
